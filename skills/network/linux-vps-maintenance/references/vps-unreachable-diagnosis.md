# Диагностика «VPS недоступен с домашнего IP» (путь/хостера, а не сервер)

Когда: SSH-таймаут, ping 100% loss с домашнего пути, хост активен в панели, консоль открывается.
Проверенный кейс: 07.08.2026 — vdska 5.39.255.242 и parafin 204.77.1.107 резались с домашнего CGNAT,
185/eurodir/babayka работали.

## Порядок проверок (каждая отсекает свой сегмент)

1. **Сервер жив? Проверь с ДАТАЦЕНТРА** (другой VPS флота, напр. 45.134.15.185):
   `sshpass -p <pass> ssh root@45.134.15.185 'timeout 6 bash -c "echo > /dev/tcp/<target>/22"'`
   Работает с DC, не работает с дома → сервер и sshd в порядке, проблема на пути/у хостера.
   ВАЖНО: ssh на заблокированный хост можно делать ЧЕРЕЗ рабочий VPS (двойной sshpass).

2. **WSL/Windows могут ходить через туннель!** Проверь реальный egress ДО тестов:
   `curl -s --noproxy '*' https://api.ipify.org`
   Если это VPS флота (46.30.47.120 eurodir и т.п.) — все «домашние» тесты невалидны,
   пакеты идут с IP VPS, а не с домашнего. Настоящий домашний путь — только с роутера
   или устройства вне туннеля. Признак: tcpdump на сервере показывает src = IP другого VPS.

3. **tcpdump на сервере — доходят ли пакеты до NIC вообще**:
   `timeout 10 tcpdump -i ens18 -n "udp and host <src>"` (после `apt-get install -y tcpdump`)
   0 packets = блокировка ДО сервера (хостера/анти-DDoS/провайдер), iptables/fail2ban ни при чём.

4. **Точечная блокировка портов** (пробой с DC и с дома, tcpdump параллельно):
   `for p in 51871 50000 42954 60240 20000; do echo probe > /dev/udp/<target>/$p; done`
   - Порт режется даже с DC = фильтр хостера на конкретный порт (анти-DDoS).
     Решение: сменить порт сервиса (в кейсе: AWG 51871 → 50000, сразу заработало с DC).
   - Порт проходит с DC, но не с дома = фильтр по источнику (CGNAT/гео/AS).

5. **MTR — где чёрная дыра**: `mtr -n -r -c 3 -w <target>`
   Обрыв внутри сети провайдера (хопы 10.64.x/10.16.x → 100% loss на следующем) =
   маршрутизация/фильтр оператора до конкретных AS (кейс: AS50053 VDSka, AS57043 HOSTKEY),
   другие AS в том же маршруте проходят. Это не чинится на сервере.

6. **DNS-порт 53 «открыт» с дома — артефакт перехвата**: провайдер отвечает на любой 53.
   Проверка: `ss -tulnp | grep :53` на сервере — если слушает только 127.0.0.53
   (systemd-resolve, loopback), то внешний «ответ» — перехват провайдера, не сервер.
   Реальный DNS-ответ (ANCOUNT=1) на запрос google.com при loopback-только = перехват.

7. **fail2ban**: на новых системах правила в nftables, не iptables (`iptables -L INPUT` пуст).
   Проверка бана домашнего IP: `fail2ban-client get sshd banned | tr ' ' '\n' | grep <home_ip>`.
   Кейс: 67 банов на parafin, домашнего IP среди них не было.

8. **CGNAT**: домашний WAN может быть 100.64.x.x (CGNAT, RFC 6598) при реальном внешнем
   178.207.x.x. Хостеры/фильтры иногда режут CGNAT-диапазон целиком как «подозрительный».

## Выводы кейса 07.08.2026
- vdska/parafin: обрыв на хопе 5 у провайдера (после 10.64.241.73 / 10.16.248.137), MTR 100% loss,
  при этом с 185 (FIRSTSERVER), eurodir, babayka — работают. Серверы не виноваты, fail2ban не виноват.
- Порт 51871 блокировался хостером VDSka даже с DC → AWG переведён на 50000.
- С домашнего CGNAT 50000 тоже не доходил — фильтр на стыке провайдер→AS (тикет оператору/хостеру).

## Рабочие обходы до решения
- SSH через прыжок: `ssh -J root@45.134.15.185 root@<target>` (или двойной sshpass).
- Webmin API с DC: `curl -sk -c /tmp/wm -d "user=root&pass=<pass>" https://<target>:10000/session_login.cgi`
  — аутентификация JSON API, дальше модульные CGI-эндпоинты. Управление с DC работает.
