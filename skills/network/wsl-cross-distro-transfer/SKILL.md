# Передача данных между WSL-образами на одной машине (мимо DLP)

## Когда использовать

- Два WSL2-дистрибутива на одной Windows-машине, нужно передать данные между ними
- Модель угроз: данные перетекают между образами мимо DLP/KES/Sysmon (контент и факт операции не должны пересекать границу Windows)
- Оценка защищённости: проверить, какие каналы между образами существуют и что из этого видно
- Проектирование защиты: как детектить несанкционированную передачу между образами

## Модель угроз (что видно и что нет)

| Слой | Статус | Механизм |
|------|--------|----------|
| Процессы внутри WSL | НЕ видны | Sysmon видит только wsl.exe, vmmemWSL |
| Файлы внутри vhdx (ext4) | НЕ видны контентному DLP | вне зоны NTFS-мини-фильтров |
| Трафик VM→VM на vSwitch | НЕ виден (в одной подсети) | не поднимается в сетевой стек Windows, нет Windows-сокета |
| /mnt/wsl (9p между дистрибутивами) | НЕ виден | vsock, не NTFS, не drvfs |
| Факт запуска двух WSL | ВИДЕН, НЕ СИГНАЛ | wsl.exe, vmmemWSL — одновременная работа образов легитимна (решение пользователя), не является аномалией для SIEM |
| Исходящие соединения из WSL | ВИДНЫ (метаданные) | Sysmon EventID 3 |
| Чтение/запись /mnt/c | ВИДНЫ | 9p/drvfs через wslhost |
| Рост vhdx, объёмы vEthernet | ВИДНЫ (агрегировано) | Zabbix-агент |
| Команды powershell.exe/cmd.exe | ВИДНЫ | EventID 1/4688, полная командная строка |

Ключевой принцип: «мимо DLP» ≠ «без следов вообще». Контент и факт файловой/сетевой операции можно скрыть, но косвенные следы (рост vhdx, прирост vEthernet-метрик) остаются. Одновременная работа двух образов в этот список НЕ входит — это легитимное состояние, не след.

## Канал 1 — файловый: /mnt/wsl (без сетевой активности)

Механика: в WSL2 при нескольких запущенных дистрибутивах каждый видит корневые ФС остальных через /mnt/wsl/<имя-дистрибутива>/. Это 9p-сервер между дистрибутивами по Hyper-V vsock — отдельная шина, не NTFS и не drvfs. DLP (NTFS-мини-фильтры) и Sysmon EventID 11 события не порождают — пути не NTFS.

⚠️ ПРОВЕРЕНО НА РЕАЛЬНОЙ ПАРЕ (Ubuntu-24.04 + Ubuntu-22.04-flash, обе WSL2, обе Running, 08.2026): КАНАЛ НЕ РАБОТАЕТ. /mnt/wsl содержит только resolv.conf, соседний дистрибутив НЕ смонтирован (проверено с обеих сторон: ls /mnt/wsl/Ubuntu-24.04 → No such file or directory). Механика зависит от версии WSL/конфигурации и на этой паре не подтвердилась. Перед использованием — ОБЯЗАТЕЛЬНАЯ проверка: `ls /mnt/wsl/` при двух запущенных. Если соседа нет — канал недоступен, использовать канал 2 или wsl.exe-посредника.

Шаги (если проверка прошла):
1. Запустить оба дистрибутива (ФС приёмника должна быть смонтирована)
2. Проверить доступность: `ls /mnt/wsl/` — должны быть подкаталоги дистрибутивов
3. Источник: записать данные, например `cp файл /mnt/wsl/<B>/tmp/`
4. Приёмник: забрать из /tmp (или другого места)
5. Очистить после передачи (rm в /tmp приёмника)

Ограничения:
- Требуется root в обоих образах (доступ к чужой ФС)
- /tmp приёмника = риск потери при перезапуске образа до забора данных
- Постоянное место приёмника = рост vhdx (виден Zabbix как рост E:/vhdx)
- Рекомендация: малый объём, разовая передача, оба образа и так активны

## Канал 2 — сетевой: трафик внутри vSwitch

Механика: оба WSL2 сидят на одном vSwitch (vEthernet (WSL)). Трафик VM→VM коммутируется на уровне Hyper-V switch и не поднимается в сетевой стек Windows → Sysmon EventID 3 не генерируется (нет Windows-сокета). Поверх — любой шифрованный транспорт.

ПРЕДВАРИТЕЛЬНАЯ ПРОВЕРКА (двухэтапная, в этом порядке):
1. СНАЧАЛА тест общности стека (loopback-тест ниже). Если стек ОБЩИЙ — канал работает через 127.0.0.1, подсети и IP не важны.
2. Если стек РАЗНЫЙ — тогда проверить: одна подсеть vSwitch И разные IP:
- `wsl.exe -d <имя-соседа> --exec sh -c "hostname -I"` (из /mnt/c, нейтральный cwd) — IP соседа
- `hostname -I` — свой IP
- `ip route` — узнать свою подсеть
- nmap соседней подсети (быстрый ping-sweep) — найти второй образ

⚠️ ПРОВЕРЕНО НА РЕАЛЬНОЙ ПАРЕ (08.2026): Ubuntu-24.04 и Ubuntu-22.04-flash имеют ОБЩИЙ СЕТЕВОЙ СТЕК. Доказательства: (а) ip addr add 172.25.5.200/20 через wsl.exe -d Ubuntu-24.04 изменил адреса в ОБОИХ дистрибутивах (и удаление — тоже), (б) слушатель на 127.0.0.1:8898 в 24.04 ПРИНЯЛ запрос curl из 22.04 к 127.0.0.1:8898 (GET записан в /tmp/24.04). Вывод: одинаковый IP у образов — признак общего стека, а не конфликта. Канал = общий loopback, ВРЕМЕННЫЙ IP НЕ НУЖЕН.

ТЕСТ ОБЩНОСТИ СТЕКА (перед каналом 2):
1. В 24.04 поднять слушатель: `wsl.exe -d Ubuntu-24.04 -u root --exec sh -c "setsid sh -c 'echo OK | nc -l -p 8898 -s 127.0.0.1 > /tmp/nc.txt &'"`
2. С моего образа: `curl -m 5 http://127.0.0.1:8898/`
3. Проверить /tmp/nc.txt в 24.04: `wsl.exe -d Ubuntu-24.04 --exec sh -c "cat /tmp/nc.txt"` — если там GET от curl — стек общий, канал = loopback

⚠️ nc годится ТОЛЬКО для теста общности (приём в файл). Для ПЕРЕДАЧИ файлов nc-слушатель ЗАВИСАЕТ (listen-режим не отдаёт stdin клиенту и не закрывает соединение — проверено 08.2026 на реальной паре). Использовать http.server или socat.

ПЕРЕДАЧА ФАЙЛА (проверено на реальной паре 08.2026, md5 совпал):
1. Приёмник-источник в 24.04 (отдаёт файл): `wsl.exe -d Ubuntu-24.04 -u root --exec sh -c "cd /tmp && setsid sh -c 'python3 -m http.server 8899 --bind 127.0.0.1 > /dev/null 2>&1 &'"`
2. Получатель в 22.04: `curl -s -m 30 -o /tmp/ФАЙЛ http://127.0.0.1:8899/ФАЙЛ`
3. Проверить целостность: `md5sum` на обеих сторонах
4. Очистка: `wsl.exe -d Ubuntu-24.04 -u root --exec sh -c "pkill -f 'http.server'"`

Шифрованный вариант (если нужен): socat+openssl на 127.0.0.1 — приёмник `socat TCP-LISTEN:PORT,fork,reuseaddr EXEC:'openssl enc -d -aes-256-cbc -pass pass:ПАРОЛЬ'`, источник `socat - EXEC:'openssl enc -aes-256-cbc -pass pass:ПАРОЛЬ' | socat - TCP:127.0.0.1:PORT`. Альтернатива: sshd на нестандартном порту с одноразовым ключом + scp.

Ограничения:
- Факт сетевой активности между VM виден в агрегате vEthernet-метрик (неотличим от фонового NAT-трафика)
- Не нужен root в приёмнике (слушатель от обычного пользователя)
- Объём не ограничен риском потери (данные у получателя сразу)

## Канал 3 — pipe через wsl.exe (base64)

Механика: передать данные через stdin процесса wsl.exe — без сетевого стека и без /mnt/wsl. Работает когда сосед доступен через `wsl.exe -d <имя>`.

Ограничение (проверено 14.08.2026 на паре Ubuntu-22.04-LTS + Ubuntu-22.04): бинарные данные через pipe НЕ проходят — wsl.exe интерпретирует stdin как UTF-8, выдаёт «stream did not contain valid UTF-8», приёмник получает пустой файл (md5 пустой строки). Текст проходит. Решение — base64-обёртка.

Шаги:
1. `--cd /tmp` обязателен — иначе wsl.exe пытается chdir в cwd источника и сыплет «chdir(-LTS/...) failed» (cwd моего образа не существует у соседа); команда при этом всё равно выполняется, но шумит.
2. `base64 файл | wsl.exe -d <B> --cd /tmp -u root --exec sh -c "base64 -d > /tmp/файл"`
3. `md5sum` на обеих сторонах (проверено 14.08.2026: совпал байт-в-байт).

Плюс: не зависит от сети/стека, работает при разных подсетях и когда /mnt/wsl пуст. Минус: +33% объёма (base64); данные идут через wsl.exe-relay (виден только факт запуска wsl.exe — легитимен). Для перезаписи скиллов: rm -rf старых каталогов + tar xzf + chown -R user:user (распаковка от root меняет владельца).

## Выбор канала

| Критерий | Канал 1 (/mnt/wsl) | Канал 2 (vSwitch) |
|----------|--------------------|--------------------|
| Root в приёмнике | нужен | не нужен |
| Сетевые метрики | ноль | прирост vEthernet (шумный канал) |
| Риск потери данных | /tmp — при перезапуске | нет |
| Рост vhdx | да (если не /tmp) | нет |
| Зависимость от подсетей | нет | нет (при общем стеке); при разных — одна подсеть |
| Шифрование | вручную (age/gpg) | стандартный тулчейн (openssl/ssh) |

Рекомендация по умолчанию: канал 2 (сетевой) — меньше привилегированных следов, нет риска потери, шифрование стандартное. Условие — общий сетевой стек (проверяется loopback-тестом) либо одна подсеть + разные IP при разных стеках. Если подсети разные при разных стеках или передача разовая малого объёма при уже активных образах — канал 1.

## Как детектить (защитная задача)

- Одновременный запуск двух дистрибутивов — НЕ сигнал (легитимное состояние), не мониторить
- Триггер в Zabbix: всплеск vEthernet-метрик в моменты, когда передача не должна происходить (вне рабочих операций)
- Периодически сверять /mnt/wsl при двух запущенных — только если канал 1 реально работает (ls /mnt/wsl показывает соседа); на проверенной паре не работает — основной детект vEthernet-метрики и рост vhdx
- Внимание к росту vhdx приёмника вне рабочих операций

## Pitfalls

- «Мимо DLP» ≠ «без следов»: косвенные метрики (рост vhdx, объёмы vEthernet) видны всегда. Одновременная работа двух образов — НЕ след (легитимна), в перечень не входит
- Образы могут иметь ОБЩИЙ СЕТЕВОЙ СТЕК (проверено 08.2026: Ubuntu-24.04 и Ubuntu-22.04-flash — одинаковый IP 172.25.5.174, loopback общий). Это НЕ препятствие, а преимущество: канал работает как общий localhost без временных IP. Проверять тестом «слушатель на 127.0.0.1 в одном, curl в другом»
- **WSLInterop (binfmt_misc) слетает между вызовами — перерегистрировать перед каждым wsl.exe.** Симптом: `/usr/bin/bash: line 4: /mnt/c/Windows/system32/wsl.exe: cannot execute binary file: Exec format error` даже на `wsl.exe --terminate`; `ls /proc/sys/fs/binfmt_misc/` показывает только register/status (WSLInterop отсутствует). Лечение (идемпотентно): `echo ':WSLInterop:M::MZ::/init:PF' > /proc/sys/fs/binfmt_misc/register 2>/dev/null;` перед КАЖДЫМ вызовом wsl.exe. Обнаружено 14.08.2026 на паре Ubuntu-22.04-LTS + Ubuntu-22.04: первая команда в сессии работала, последующие падали, пока не добавил перерегистрацию. Проверка после: `cat /proc/sys/fs/binfmt_misc/WSLInterop`.
- /mnt/wsl не гарантирован: на проверенной паре (два запущенных WSL2) соседний дистрибутив НЕ монтируется — только resolv.conf. Всегда проверять ls /mnt/wsl до выбора канала 1
- Канал 2 в разных подсетях не работает начисто — проверка ip route/nmap обязательна до выбора
- /mnt/wsl требует запущенных обоих образов — окно передачи ограничено временем совместной работы
- /tmp приёмника — данные пропадут при перезапуске; постоянное место — рост vhdx
- nc-слушатель ЗАВИСАЕТ при передаче файлов (listen-режим не отдаёт stdin клиенту, соединение не закрывается — проверено 08.2026). nc — только для теста общности стека (приём в файл); передача — через python3 http.server (проверен) или socat
- Не использовать powershell.exe/cmd.exe как посредника (полная командная строка видна — EventID 1/4688)
- Clipboard (WSLg) — виден (clip.exe), малая ёмкость — не канал
- Windows-процессы — только при крайней необходимости, короткие нейтральные команды (правило wsl-fortress)

## Верификация

- Канал 1: ls /mnt/wsl показывает оба дистрибутива; запись/чтение тестового файла. НА ПРОВЕРЕННОЙ ПАРЕ НЕ ПРОШЁЛ (/mnt/wsl пуст)
- Канал 2: НА ПРОВЕРЕННОЙ ПАРЕ ПРОШЁЛ — (а) тест общности: nc на 127.0.0.1:8898 в 24.04 принял GET от curl из 22.04; (б) передача реального файла (41К docx) через python3 http.server на 127.0.0.1:8899 — md5 совпал на обеих сторонах
- Рабочий минимум на паре с общим стеком: слушатель на 127.0.0.1 в одном, клиент на 127.0.0.1 в другом — при ОБЩЕМ стеке loopback-трафик не даёт прироста vEthernet-метрик и файловых операций; при РАЗНЫХ стеках трафик VM→VM виден в агрегате vEthernet (см. модель угроз)
- Проверка следов: zabbix-метрики vEthernet до/после (прирост при обмене по 172.25.x; при loopback — прироста нет)
