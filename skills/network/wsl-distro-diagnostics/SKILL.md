# Диагностика соседнего WSL-образа (изнутри WSL)

## Когда использовать

- Соседний WSL-дистрибутив (вторая Ubuntu и т.п.): сервис/сеть/приложение «сломалось» — зайти, посмотреть логи, проверить сеть, сравнить окружения
- Прогнать пробу/скрипт в соседнем образе без копирования файлов через Windows (лишние следы на Windows/DLP не нужны)
- Сравнить два образа: версии пакетов, пути установки, конфиги, поведение сети

## Базовый доступ

1. Перерегистрация binfmt WSLInterop ПЕРЕД КАЖДЫМ вызовом wsl.exe (идемпотентно):
   `echo ':WSLInterop:M::MZ::/init:PF' > /proc/sys/fs/binfmt_misc/register 2>/dev/null`
   Симптом пропуска: «cannot execute binary file: Exec format error». Полный разбор — wsl-cross-distro-transfer (pitfall 14.08.2026).
2. Вызов: `wsl.exe -d <имя> --exec sh -c '...'`
   - Имя дистрибутива: `wsl.exe -l -v | cat` (вывод UTF-16 с \u0000 — через cat читается)
   - cwd: если текущий каталог не существует в целевом образе, wsl.exe печатает «<3>WSL ERROR: chdir(...) failed 2» — это шум, команда выполняется. Для чистоты вывода: `cd /mnt/c` перед вызовом.
   - Пользователь: default user образа (может быть `user`, не root) — первым делом `whoami`.

## Прогон многострочного скрипта — base64 через stdin

Вложенные кавычки (`sh -c 'python -c "..."'`) ломаются на первом же апострофе. Надёжный путь (проверен на паре Ubuntu-22.04-LTS + Ubuntu-22.04):

1. Локально: `write_file /tmp/probe.py`
2. `B64=$(python3 -c "import base64; print(base64.b64encode(open('/tmp/probe.py','rb').read()).decode())")`
3. `echo "$B64" | wsl.exe -d <имя> --exec sh -c 'base64 -d > /tmp/probe.py && <venv-python> /tmp/probe.py'`
   — wsl.exe пробрасывает stdin в процесс; скрипт сам читает ключи/конфиги из целевого образа.

## Сетевой слой соседа (5 проверок)

1. `curl -s -m 12 -o /dev/null -w "%{http_code}" https://<endpoint>` — 401/403/200 = соединение ЕСТЬ (код — про авторизацию, не про сеть); 000 = сети нет
2. `env | grep -iE "proxy|http"` — прокси-переменные
3. `getent hosts <домен>` — DNS
4. `curl -4` vs `curl -6` — разделить IPv4/IPv6
5. `hostname -I` на ОБОИХ образах: одинаковый IP = общий сетевой стек. Тогда: один образ ходит в интернет, другой нет → проблема локальна для второго (клиент/конфиг/тайминг), физический путь ни при чём.

## Процессы и логи

- `ps aux | grep -iE "hermes|python"` — как установлен и запущен процесс (пути venv/bin, .local/bin), PID, время старта
- `ss -tnp | grep <pid>` — живой процесс БЕЗ сокетов = ждёт ввода после ошибки (CLI), а не «висит в цикле ретраев»
- ЛОГ-ЛОВУШКА: `grep ... | tail` на большом логе возвращает последние СОВПАДЕНИЯ, которые могут быть месячной давности (agent.log живёт годами). Сверять: `date` в целевом образе, mtime файлов лога, session-id в строках. Свежие строки — только `tail` без grep (или отдельный errors.log).

## Паттерн «транзиентный vs системный» (ошибки провайдера/сети при старте)

Ошибка «не могу достучаться до провайдера» при старте часто РАЗОВАЯ (NAT/DNS/CloudFront моргнули). Прежде чем править конфиг или код — воспроизвести независимо:

1. curl до endpoint (401/403 = сеть ок)
2. Стриминг-зонд ТЕМ ЖЕ python-стеком приложения (venv), тем же ключом, ТЕМ ЖЕ размером контекста: большой POST (~28K токенов / сотни КБ) рвётся там, где маленький проходит — MTU/промежуточное устройство. Зонд = маленький + большой запрос.
3. Пробы прошли, приложение упало в момент старта и после «Final error» молчит — транзиент, фикс = перезапуск.
4. Падает стабильно на каждом старте — системно: сравнить версии (`git log` в каталоге установки), обновить, копать errors.log.

Полный кейс: references/hermes-transient-apiconnectionerror.md

## Питфолы

- Не доверять датам в логе по grep+tail — проверять вручную (date, mtime, session-id)
- Не менять конфиг/код соседа, пока независимые пробы (curl + зонд) не подтвердили, что сбой воспроизводится
- chdir-ошибка wsl.exe — шум, не ошибка
- Одинаковый IP у образов = общий сетевой стек, не конфликт (см. wsl-cross-distro-transfer)
- Имя дистрибутива точное: `Ubuntu-22.04` ≠ `Ubuntu-22.04-LTS`

## Верификация

- Каждый вывод диагностики подкреплён реальным выводом (curl-код, зонд OK/FAIL, ss, ps)
- Правило контр-пробы: при «не работает» показать, что работает (тот же стек, тот же endpoint, тот же ключ) — это отличает транзиент от поломки
